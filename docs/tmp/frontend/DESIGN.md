# Frontend Scaffold — Design

## Overview

Next.js (App Router) + React + Tailwind frontend for the work-sim prototype.
Three screens, polling-based live updates, no global state library, no UI
component library. Talks to the existing Fastify API at
`apps/api/src/routes/runs.ts`.

## Motivation

- The locked decision (now updated) chose Next.js over Vite. Even though the
  prototype is purely client-rendered, Next gives us file-system routing
  (no `react-router`), a polished dev server, and a clean upgrade path to
  server components / route handlers / SSE without rewriting.
- Wire shapes and presets are imported from `@work-sim/shared`, so the form
  and API client never re-declare types.

## Key design decisions

| Decision | Rationale |
|---|---|
| All pages are client components (`"use client"`) | Polling + form state + localStorage drafts all need the browser. No data needs server rendering, and there's no auth. |
| Talk directly to Fastify via `NEXT_PUBLIC_API_URL` (cross-origin) | Simpler than configuring `next.config.ts` rewrites; CORS is already set on the API for `localhost:3000`. Switching to a rewrite later is one config change. |
| Polling via chained `setTimeout` (not `setInterval`) | Avoids overlapping in-flight requests. Cleanly cancellable on unmount. |
| Local `useState` everywhere; no Redux/Zustand/Jotai | Three screens, none share state. The server is the source of truth. |
| Recharts for the two charts | Tiny, declarative, sufficient. Marked as a new dep to add. |
| Persist setup-form draft in `localStorage` under `'work-sim:setup-draft'` | Reload-safety; matches the doc. |

## Data flow

```
                     ┌─ /                (runs list, useRuns polls every 5s)
Next.js App Router ──┼─ /new             (setup form, posts to /runs)
                     └─ /runs/[id]       (run detail, useRunPolling every 2s)
                            │
                            ▼
                    lib/api.ts  ── fetch ──▶  Fastify @ NEXT_PUBLIC_API_URL
                                              GET /runs, POST /runs, GET /runs/:id
```

## Open questions

- Should the runs list page be a server component with `revalidate` instead of
  client-side polling? Simpler in some ways, but mixed with client polling
  for in-progress runs gets awkward. Punted: stay all-client for v1.
- Do we want a Next `rewrites` proxy so the frontend can call `/runs` same-
  origin? Slightly nicer DX but means the API URL is hardcoded in
  `next.config.ts` rather than env. Punted: env-based.
